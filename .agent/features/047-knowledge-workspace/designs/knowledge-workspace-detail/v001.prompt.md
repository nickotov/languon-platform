# Knowledge workspace detail page — design prompt v001

Copy the entire block below into Magic Patterns. The [design handoff](../../.agent/features/047-knowledge-workspace/DESIGN.md) freezes this revision; the [workspace requirements](../../.agent/features/047-knowledge-workspace/FEATURE.md) and [user flow](../user-flows/knowledge-workspace.md) remain authoritative for implementation.

```text
Redesign ONE EXISTING SCREEN in Languon, a language learning app for adults: the private Knowledge note editing workspace. Produce a polished, realistic, responsive interactive prototype. The current page feels like a long stack of form fields and disconnected action blocks. Make writing the visual center and keep the AI tutor close at hand without obscuring the document. Preserve the behavior below; do not invent new product capabilities.

VISUAL DIRECTION
Quiet editorial workspace, clear hierarchy, generous but efficient spacing, refined typography, restrained borders and shadows, accessible contrast. Use the existing app's light palette as a cue: soft gray background #f8f9fb, white surfaces, near-black text #1b1e24, subtle borders #e4e7ec, indigo accent #4f46e5. Also show a credible dark variant using #121417 background, #1b1e24 surfaces and #818cf8 accent. This is a serious study and writing tool, not a marketing dashboard. Use realistic content such as a note titled “Why ‘ser’ and ‘estar’ change meaning,” with English explanation, Spanish examples, a quotation, list and small table. Keep navigation visibly part of the existing authenticated app; redesign the workspace, not the whole app shell.

DESKTOP LAYOUT (show at 1440 px and ensure it still works at 1280 px)
- A document editor is the primary left pane; a reusable Language tutor is docked on the right. The page and tutor must remain independently usable and scrollable. The tutor normally takes a compact side width. Its settings popover includes a control that expands the docked tutor to 50% of the available content width. The same settings allow a detached floating chat. Show the layout in both compact and equal-width states.
- A compact document header contains Back to Knowledge, one editable title, Draft or saved state, private draft recovery status and a prominent Save action. Do not display the title twice as a large heading and a separate form field. Save a copy, revision history and Delete are available as secondary actions; Delete requires confirmation. Place messages and errors near the action they affect.
- Put the rich-text editor high on the page, with a calm writing surface, useful line length and a toolbar that is discoverable without dominating the document. Existing controls include paragraph/headings, emphasis, lists, quote, link, table and undo/redo. Text selection must be obvious because it can be sent to the tutor and can be the target of an AI proposal.
- Title and nonempty editor content are required to Save. Summary, categories and language metadata are optional. Group optional metadata in a clearly accessible secondary area or disclosure so it does not push the editor far down the page. Do not imply that recovery automatically publishes changes.
- Sharing controls belong to the explicitly saved note, not the working draft. Keep them visible but subordinate: Enable sharing, Copy read-only link and Disable sharing as appropriate. A new link is created after sharing is re-enabled. The shared version is the last explicit Save; unfinished edits, conversations and attached references remain private.

TUTOR AND RESEARCH LOGIC
- Reuse the existing Language tutor, including new conversation, private conversation history and conversation deletion. Reopening this note opens its most recent chat. New chats start with the current document as context but never inherit another chat's history or copied references. A note can have an empty document and an active chat. The first message gives an Untitled note a title from its first three words only while that default name remains unchanged; each chat gets its own title.
- Every sent message gives the tutor the complete current editor snapshot, including unsaved edits, within a separate configurable editor character limit (currently 40,000 plain-text characters). A selected passage focuses the question while the surrounding document is still available. Later edits reach the tutor on the next message. Do not imply live awareness between sends.
- The composer supports adding copied Text references with / or Add context, including a translation only when selected. Preview attached content with a thin readable wrapper while the actual text is sent to the tutor. All selected reference bodies together have a separate 40,000-character limit including whitespace; an addition that would exceed it is rejected as a whole with a clear toast. This is a copied-content flow, not a document upload or external search flow.
- Tutor replies stay in chat. A user can explicitly turn a reply into a document proposal: Insert at remembered cursor, Append to current document end, or Replace the remembered selection. Show a clear review/accept step and one undoable edit on acceptance. If the original target changed or disappeared while the proposal was generated, compare original/current/proposed text and require a fresh decision; moving the cursor alone must not retarget it.
- Include realistic streaming and thinking states, Stop, retry/error and an empty conversation. The tutor is constrained to language learning and acknowledges uncertainty; do not present it as a web search assistant or show fabricated citations. Future uploads, media embeds and RAG are outside this design.

REQUIRED STATES TO PROTOTYPE
1. Fresh private Untitled Draft: stable note identity, empty editor, chat usable, private recovery indicator; Save unavailable until title and body exist; no sharing controls. It appears in Knowledge with a Draft label and can be reopened or deleted.
2. Working saved note: editor with content, compact docked tutor, optional metadata, Save, Save a copy, history and saved-only sharing. Show the 50% docked tutor setting and detached option as interactive controls.
3. Unsaved edits: visible saving/recovered/local-change/error status for private server draft recovery. Explicit Save updates the saved note and its shared view. Save a copy creates an independent saved note from the current working draft, without chats, attached references or earlier revisions.
4. Concurrent edits: two tabs/devices have different working versions. Preserve both and show comparison with options to continue either, manually combine, or save one as a separate note. Require explicit resolution and never silently overwrite prose.
5. Proposal review and stale target: show insert/append/replace choices, remembered target, original/current/proposed comparison when target changed, a choice of new target, and undo after acceptance.
6. Revision history, restore confirmation and interaction with unsaved changes; missing/permission errors; unsaved navigation and delete confirmations. Keep failure copy concise and actionable.
7. Shared reader example only as a secondary state: unlisted read-only link exposes the last saved note content. A signed-in recipient can save an independent copy. Never show private chat, draft recovery, references or earlier revisions to a reader. Disabling sharing invalidates that link immediately; later sharing creates a new link.

RESPONSIVE AND ACCESSIBILITY
- At 390 px and 320 px, the document remains primary. The tutor becomes a bottom sheet with a clear launcher, useful peek/expanded states, safe keyboard behavior and controls that do not cover the editing caret or Save action. The tutor can be dismissed without losing the document draft or chat. At intermediate widths, keep document text readable rather than crushing both panes.
- Support keyboard navigation, visible focus, sensible touch targets, accessible status announcements, reduced motion, long/localized labels, and RTL content where relevant. Show empty, loading, error and success states without relying on color alone.

DELIVERABLE
Create an interactive prototype rather than a static hero mockup. Show at least desktop Draft, desktop saved document with tutor (compact and 50% widths), proposal/conflict overlays, and mobile bottom sheet. Make title/body editing, optional metadata, Save, chat switching, reference preview, tutor width/detach settings, proposal acceptance, history, and share controls demonstrable with local demo state. Use realistic text and controls; avoid decorative controls that imply unsupported behavior.
```

## Review checklist

- **KW-D01:** The document and one editable title dominate the page; optional metadata is accessible without delaying writing.
- **KW-D02:** The reused tutor docks on the right, supports 50% width and detachment, and becomes a bottom sheet on mobile.
- **KW-D03:** Private recovery, explicit Save, saved-only sharing, Save a copy and Draft are distinct.
- **KW-D04:** A chat can start with an empty document; conversation history and references stay private and independent.
- **KW-D05:** The editor snapshot, selected passage and copied Text references have accurate send-time and limit semantics.
- **KW-D06:** Replies remain chat content until an explicit, undoable document proposal is accepted.
- **KW-D07:** A stale proposal target and concurrent draft versions require comparison and user resolution.
- **KW-D08:** Shared readers see only saved content and can create independent copies.
- **KW-D09:** Desktop, mobile, dark mode, keyboard, loading and error states are represented.
- **KW-D10:** The prototype does not promise web search, citations, upload, RAG or media editing.
