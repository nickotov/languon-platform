# Reliable continuation after a lesson pauses

## Incident and scope

The November 18 investigation distinguished two runs on one Knowledge note. The newer run saved reading material and an exercise checkpoint. Its next generation stage recorded a transport failure after 24 seconds. The older run retained three of four grammar exercises and an answer-key validation failure. The rejected Continue targeted that older run. The HTTP response body was unavailable, so its precise rejection code remains unknown. No live retry or balance change was necessary for diagnosis.

The browser transport independently reproduced an idle reconnect deadlock. After the server rotated the SSE connection, a successful replacement stream delivered only heartbeats. The UI continued to disable the action that could produce the next event. The source review also found cumulative checkpoint bodies entering minimum-input admission, a shared 120-second stage deadline omitted from the next-call budget, runner fallback missing durable callbacks, and dropped automatic-admission failure reasons.

This extends feature 071 on its existing branch. Current authorization, price limits, ownership checks, revision fences and checkpoint validation remain binding under ADR-0060 and ADR-0061. A long lesson can span multiple bounded stages. Reaching the eight-stage, fifteen-minute or credit boundary must leave recoverable progress with an explicit reason.

## Implementation sequence and acceptance

1. **Observation and command identity.** Acknowledge a healthy replacement stream even when idle, reconcile the selected run history once per gap, and unlock actions once authoritative state arrives. Scope each action, response and error to its actor, conversation and run. Persist a stable semantic command ID for ambiguous retries where safe. Distinguish an HTTP admission rejection from an interrupted worker attempt and surface actionable localized information on the right card. Verify a heartbeat-only reconnect and a conversation switch between two runs on one note.
2. **One input calculation per unfinished unit.** Resolve the first missing unit against validated current-revision checkpoints. Select declared dependencies and relevant prior exercise material once and share the projection with admission and dispatch. Keep the full saved artifact chain for preview, validation and audit. Preserve the actual model input ceiling, idempotency and rejection for a genuinely oversized required dependency. Verify an oversized history with a fitting final unit and a truly oversized dependency.
3. **Time-aware durable execution.** Include remaining stage time in admission of each new tool call, retain per-call deadlines, reserve repair headroom, and hand off before starting a unit too close to its deadline. Reuse stable checkpoint identity and resume the first missing unit. Ensure route fallback cannot replay durable side effects after a checkpoint, including when new tools are added. Exercise late-stage dispatch, fresh-stage progress, cancellation and fallback after the first durable effect.
4. **Classified failures and recovery.** Persist sanitized outcomes and the action required for execution and automatic admission. Differentiate capacity/rate limits, exhausted authority, invalid input/output, interrupted connections and ambiguous provider dispatch where evidence permits. Bound safe transient retries with backoff and existing authority. Fence concurrent retries and avoid replay after ambiguous dispatch. Ensure the client can show the specific reason after reload. Verify that failure recording does not silently discard unexpected infrastructure errors or report an old pause reason.
5. **Verification and documentation.** Run focused web transport/card, backend admission/clock/fallback, contract and accounting tests while implementing (seconds to a few minutes each). Exercise worker persistence and retries with disposable PostgreSQL/Redis, then run affected Knowledge browser journeys and real rendered recovery checks (several minutes each). Verify saved IDs, provider attempts, selected run, request counts and settlement together. Update the existing guide, mapped test, architecture and feature evidence. Run affected typechecks, builds, docs checks and local conversation capability doctor. Require independent source and evidence review. Record live provider verification separately from deterministic checks.
