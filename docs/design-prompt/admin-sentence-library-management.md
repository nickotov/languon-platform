# Per-user admin sentence management — Magic Patterns prompt

Versioned owner: [feature 039](../../.agent/features/039-sentence-library-management/FEATURE.md).
[Design registry](../../.agent/features/039-sentence-library-management/DESIGN.md).
[Implementation plan](../sentence-library-implementation-plan.md).

Copy the complete brief below into Magic Patterns. It describes verified backend
behavior and the frontend to design. It contains no concrete API paths.

---

Design a focused sentence-management section inside Languon's existing per-user
administration interface. Use Russian copy and the established Ant Design/Refine
admin visual language: compact tables, clear form labels, drawers, confirmation
modals, consistent spacing and restrained danger styling. Preserve the current
admin application shell, navigation, user identity/context and unrelated user
management controls. Create an implementable responsive prototype using fake data.

## Product context and precise terminology

Admins need to inspect and manage saved sentence examples relevant to a selected
user. Sentences can be shared. A personal archive affects one learner, while a
global archive excludes the example from everyone's future practice. Ordinary
archive preserves learning history; permanent deletion erases associated content
and answers for every affected learner and cannot be undone.

“Автор скрыл у себя” means the generator personally archived the example. The
creator may differ from the user whose admin page is open. Permanent deletion is
allowed only for creator-archived examples. Do not confuse a target learner's
personal archive with the creator's personal archive or with global archive.

This feature manages examples; it does not edit their sentence text, reference,
hints, answers or scores. Preview does not create a learner exposure/review.
Do not add AI generation/checking or admin practice controls.

## 1. Per-user entry point and dictionary discovery

Add “Предложения” within the current user's detail area. Keep the selected user's
name/email or existing identifier and account status visible so actions cannot be
mistakenly applied to another user. Avoid a detached global sentence database page.

First discover dictionaries relevant to the user through ownership, generation,
recorded practice exposure or preparation. Present a bounded searchable-looking
selection/list only if real filtering is supported; otherwise use pagination and
clear dictionary labels rather than inventing a server search feature. Do not
claim this is a catalogue of every unlisted dictionary the user could access.

Each dictionary entry should show title, language pair and available/generated
example counts. Explain these as different measures; examples generated by the
user can include ones currently unavailable for their practice. Show initial
loading, zero relevant dictionaries, next-page loading, retryable failures and
stale/unavailable selection states. Preserve user context when changing dictionary.

Use a realistic French/Russian dictionary with examples in both translation
directions. Show “Русский → Французский” or “Французский → Русский”; don't use
ambiguous source/target technical terminology as the sole label.

## 2. Example table and filters

Place a compact toolbar above a paginated table with:

- Dictionary and direction context.
- Available-to-user / generated-by-user / both relationship filter.
- Personal archive: active / archived / all.
- Global archive: active / archived / all.
- Currentness: current / outdated / all.
- Creator-archived filter, explicitly labelled “Автор скрыл у себя”.
- Clear filter reset and selection controls.

Initially select “Все” for relationship, personal archive and global archive so
target-generated archived examples remain inspectable; submit those explicit
filter choices rather than assuming a public-list default. Administrative lists
may include globally archived examples. Represent availability
as independent conditions, not one misleading archived boolean. Include concise
badges/tooltips where simultaneous states need clarification.

Table rows should contain selection, sentence snippet, direction, creator identity
as permitted in admin, creation date, currentness, target-user personal visibility,
global visibility and creator-archive eligibility. A compact details action opens
a drawer. Long sentences should wrap or clamp with full text available in preview.
Use clear column grouping so target-user and creator states are distinguishable.
For creators, label “Этот пользователь” or “Другой автор”; use the supplied
administrative identifier in detail if needed. Do not invent creator names/emails
when those are absent from the data. Keep table width manageable; on narrow screens prioritize sentence/action/state
and move supporting metadata into expandable details rather than hiding risk.

Never expose raw job IDs, prompt bodies, shared keys, financial reservations or
internal diagnostics as ordinary table content. Do not invent practice statistics
not supplied by the management data.

## 3. Read-only detailed preview

Use an accessible drawer/detail area with the selected user and dictionary context.
Show sentence, direction, date, creator, currentness and each archive layer.
Provide an expandable “Пример перевода” and all saved dictionary mappings and
additional word/whole-phrase hints. Preserve whole expressions such as
“avoir besoin de”; do not break their meaning into separate token translations.

Example:

- Russian sentence: “Мне нужна помощь после работы.”
- French reference: “J'ai besoin d'aide après le travail.”
- Dictionary mapping: “после работы” → “après le travail”.
- Phrase hint: “avoir besoin de” — “нуждаться в”.
- Additional hint: “aide” — “помощь”.

Include a legacy item with only dictionary hints and explain that additional
context hints are absent. No editable fields or save-content button belong here.
Preview remains free and does not alter the target learner's statistics.

## 4. Distinct administrative actions

Present action scope explicitly:

1. “Скрыть для этого пользователя” / “Восстановить для этого пользователя”.
   This changes the target user's personal practice visibility.
2. “Скрыть для всех” / “Восстановить для всех”.
   This changes global practice visibility while preserving history.
3. “Удалить навсегда”. This is a separate destructive action, enabled only when
   the generator personally archived the example.

Keep irreversible removal visually separate from routine archive/restore. Explain
why it is disabled on an ineligible row: “Сначала автор должен скрыть пример у себя”.
Do not give administrators a shortcut to manufacture eligibility by marking a
non-target creator archived through this screen.

Restoration can leave another exclusion in place: restoring personal visibility
cannot undo global archive, and restoring either cannot fix outdated vocabulary.
Show the resulting usability honestly. History-preserving archive and permanent
content removal must have different confirmation language.

All mutations require a meaningful reason and recent authentication. Use the
existing administrative reason-form conventions; do not invent an extra approval
workflow or an AI explanation. Preserve the reason and selection when an operation
needs reauthentication or encounters a retryable failure.

## 5. Selected and all-matching operations

Support individual selection, current-page selection and an explicit all-matching
selection across pages. Show honest counts and active filter scope. Changing the
user, dictionary, filters or action scope must clear or reconfirm selection.
Do not silently carry a destructive selection into another user's page.

A contextual toolbar should show the applicable actions, affected count, selected
scope and clear-selection control. Bulk confirmations describe the frozen set and
its exact count. Don't present “all” when only the visible page is selected.

For personal archive, confirmation names the target user. For global archive,
confirmation names the all-learners consequence. For irreversible delete:

- Clear danger heading and exact count/dictionary/filter scope.
- Explicit explanation that sentence content and associated answers are removed
  for every affected learner, permanently.
- Explanation that creator-archive eligibility is checked again at execution.
- Required reason and a deliberate separate confirmation step.
- Accessible final destructive button, distinct safe cancel, no undo promise.
- Use a typed “УДАЛИТЬ” confirmation if consistent with existing admin destructive
  forms; the prototype must make the acknowledgement deliberate and visible.

Do not invent a number of affected learners if the data supplies only the selected
example count. Do not display accounting records or suggest financial history is
editable through this feature.

During submission, retain context/selection/reason, disable duplicate mutation and
show a clear pending state. On success, refresh the relevant counts, badges and
list and show a concise result notice. Permanent deletion closes unavailable
preview content; archive can remain inspectable under the correct filters.

Confirmation sets can expire, be superseded or become stale after card/archive
changes. Show “Выбор изменился. Проверьте набор и подтвердите снова.” instead of
silently applying a different set. Retain the administrator's reason where safe.
There are at most five live confirmations per actor/dictionary and 25 per actor;
all-matching confirmations support at most 10,000 examples. Explain narrowing
filters or selecting smaller groups when that limit is reached.

## 6. Authentication, busy work and recovery

If recent authentication is missing, route through the existing admin
reauthentication UX and clearly return to the same selected user/action. Do not
stack a second full-size dialog on top of the destructive confirmation. Retain
selection intent/reason but revalidate content before enabling submission again.

If the admin session expires or membership is revoked, stop further actions,
remove privileged content where appropriate, and show the established safe
sign-in/access-denied route. A target user scheduled for deletion/purged or a
removed dictionary is an unavailable target, not a generic spinner forever.

Permanent deletion can be blocked by generation/check work that has not settled.
Show “Пример ещё обрабатывается. Дождитесь завершения и повторите удаление.” Keep
the selection/reason and offer a safe retry after refreshing eligibility. Do not
pretend a purge succeeded or automatically cancel/refund another learner's work.

An uncertain network result should recover the operation's actual result before
offering a duplicate destructive submission. Retry should be safe and clearly
labelled; do not expose receipt IDs or database internals to admins.

## 7. Required prototype states

Create separate named variants with complete controls and copy for:

- Relevant dictionary loading/list/empty/load failure/pagination failure.
- Sentence table loading, successful populated list, no examples, no filter results.
- Available-to-target example created by someone else; target-generated example;
  creator-archived example whose creator differs from the selected user.
- Personally archived, globally archived, both, current/outdated combinations.
- Detail loading, detail error, no extra hints, long multilingual content.
- Selection across pages versus page-only selection, clear/reset selection.
- Personal/global archive and restore confirmation, reason validation, pending,
  success, failure, and restoration that still leaves another exclusion.
- Permanent deletion eligible/ineligible, explicit irreversible confirmation,
  pending, success, retryable busy work, and example removed concurrently.
- Expired/superseded confirmation, card/version changed after selection, oversized
  all-matching set and fresh-reconfirmation flow.
- Recent-authentication required, returning from reauthentication, authentication
  failure, session expiry and admin membership revoked.
- Target scheduled for deletion/purged, dictionary unavailable and access lost.
- Slow/uncertain requests with retained context, operation-result recovery, transient
  failure and retry without duplicate effects.
- Mobile/narrow-width table/detail/confirmation layouts and keyboard-only use.

## 8. Visual and interaction deliverables

Use the current admin tokens/components, restrained status colors and clear density.
Keep destructive labels readable and precise. Respect focus trapping/return,
escape/cancel behavior, visible keyboard focus, screen-reader labels, status
announcements, contrast, reduced motion, long names/text and RTL-capable layouts.
Keep the selected user's context visible during drawer and confirmation workflows.

Build interactive journeys for dictionary selection → preview → personal archive
→ restore, filtered all-page selection → global archive, and creator-archived
selection → recent authentication → permanent deletion with busy/retry variants.
Use fake data and simulation; no live destructive requests.

Deliver desktop/mobile user-detail integration, dictionary selector, table/filter
states, read-only detail drawer, each confirmation type and all material recovery
states. Separate demonstration controls from product UI. Provide enough detail
for faithful implementation; do not add text editing, AI generation, new approval
roles or concrete API routes.
